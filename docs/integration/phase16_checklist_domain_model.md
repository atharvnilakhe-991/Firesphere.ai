## 3. Checklist Domain Design

The domain model implements five core concepts structured for regulatory compliance (NBC 2016 Part 4):

### A. ChecklistTemplate (`ChecklistTemplate.java` -> `firesphere.inspection_checklists`)
- Template identifier (`id`, UUID).
- Template code (`template_code`, e.g., `NBC_2016_COMMERCIAL`, `NBC_2016_RESIDENTIAL`).
- Template name (`template_name`).
- Version (`version`, e.g., 1).
- Inspection type (`inspection_type`, e.g., `COMMERCIAL`, `RESIDENTIAL`, `INDUSTRIAL`).
- Regulatory source authority (`source_authority`, e.g., `NBC 2016 Part 4 Table 7`).
- Active status (`is_active`, boolean).
- Audit timestamps (`created_at`, `updated_at`).

### B. ChecklistTemplateItem (`ChecklistTemplateItem.java` -> `firesphere.inspection_checklist_items`)
- Item identifier (`id`, UUID).
- Parent template link (`checklist_id`).
- Stable item code (`item_code`, e.g., `EXT-01`, `EXIT-01`, `HYD-01`, `ALM-01`).
- Item title (`item_title`).
- Section category (`category`, e.g., `FIRE_EXTINGUISHERS`, `MEANS_OF_EGRESS`, `HYDRANT_SYSTEM`).
- Requirement text (`requirement_description`).
- Statutory mandate (`is_mandatory`, boolean).
- Evidence mandatory flag (`evidence_required`, boolean).
- AI category tag (`ai_category_tag`, e.g., `FIRE_EXTINGUISHER`, `FIRE_EXIT`, `SMOKE_DETECTOR`) for advisory cross-referencing.
- Display sort order (`display_order`).

### C. InspectionChecklist (`InspectionChecklist.java` -> `firesphere.inspection_checklist_instances`)
- Checklist instance identifier (`id`, UUID).
- Multi-tenant ID (`tenant_id`, UUID).
- Inspection reference (`inspection_id`, UUID, Unique 1:1).
- Template snapshot code (`template_code`) and version (`template_version`).
- Lifecycle status (`lifecycle_status`: `DRAFT`, `IN_PROGRESS`, `COMPLETED`).
- Initialized officer (`created_by_officer_id`).
- Completed officer and timestamp (`completed_by_officer_id`, `completed_at`).

### D. InspectionChecklistResponse (`InspectionChecklistResponse.java` -> `firesphere.inspection_checklist_responses`)
- Response identifier (`id`, UUID).
- Instance link (`checklist_instance_id`).
- Template item reference (`item_id`).
- Officer response status (`status`: `COMPLIANT`, `NON_COMPLIANT`, `NOT_APPLICABLE`, `NEEDS_FURTHER_INSPECTION`, `NOT_REVIEWED`).
- Officer remarks (`remarks`, mandatory when status != `COMPLIANT`).
- Responding officer identifier (`officer_id`).
- Audit timestamps (`responded_at`, `created_at`, `updated_at`).
- Revision tracking (`revision_number`).
- Supporting evidence list (`evidence_attachments`).
- Advisory AI links (`ai_finding_links`).

### E. ChecklistFindingLink (`ChecklistFindingLink.java` -> `firesphere.checklist_finding_links`)
- Link identifier (`id`, UUID).
- Checklist response reference (`response_id`).
- AI finding reference (`finding_id`).
- Provenance (`provenance`: `AI_SUGGESTION`, `OFFICER_CONFIRMED`, `MANUAL_ASSOCIATION`).
- Link status (`link_status`: `SUGGESTED`, `ACCEPTED`, `DISMISSED`, `SUPERSEDED`).
- Review metadata (`reviewed_by_officer_id`, `reviewed_at`, `officer_notes`).

## 4. Response and Review Semantics

Strict statutory validation rules are enforced in `InspectionChecklistService.java`:
1. **Non-Compliant Validation:** When an officer marks an item `NON_COMPLIANT`, non-blank remarks specifying the statutory defect are strictly required.
2. **Not Applicable Validation:** When an officer marks an item `NOT_APPLICABLE`, mandatory justification remarks must be recorded for audit defense.
3. **Further Inspection Validation:** When marked `NEEDS_FURTHER_INSPECTION`, remarks detailing the required follow-up action are required.
4. **Mandatory Evidence Enforcement:** If `evidence_required` is true for the checklist item, saving a `COMPLIANT` response requires at least one attached evidence item (`checklist_response_evidence`) or an explicit reference.
5. **Decoupled AI Advisory Status:** Linked AI findings do not overwrite officer responses. An item with AI suggestions remains `NOT_REVIEWED` until an authorized inspecting officer explicitly submits their determination.
6. **Authorization & Response Protection:** An inspecting officer cannot overwrite another officer's recorded checklist response without `ROLE_STATION_OFFICER` or `ROLE_ADMIN` supervisory authority.
7. **Completion Gate:** A checklist cannot transition to `COMPLETED` lifecycle status if any mandatory item remains in `NOT_REVIEWED` status.

## 6. API Contract

The REST API contract is implemented under `/api/v1/inspections` in `InspectionChecklistController.java`:

### 6.1 Available Endpoints

| Method | Endpoint | Description | Required Roles |
|---|---|---|---|
| `GET` | `/api/v1/inspections/checklist-templates` | List active checklist templates | Officer, Station Officer, Admin |
| `POST` | `/api/v1/inspections/{inspectionId}/checklist` | Initialize checklist instance from template | Officer, Station Officer, Admin |
| `GET` | `/api/v1/inspections/{inspectionId}/checklist` | Retrieve checklist instance and responses | Officer, Station Officer, Admin |
| `GET` | `/api/v1/inspections/{inspectionId}/checklist/items/{itemId}` | Get item detail with AI links and evidence | Officer, Station Officer, Admin |
| `PUT` | `/api/v1/inspections/{inspectionId}/checklist/items/{itemId}/response` | Record or update officer response | Officer, Station Officer, Admin |
| `POST` | `/api/v1/inspections/{inspectionId}/checklist/items/{itemId}/ai-links` | Link AI finding suggestion to item | Officer, Station Officer, Admin, System |
| `PATCH` | `/api/v1/inspections/{inspectionId}/checklist/items/{itemId}/ai-links/{linkId}` | Review AI suggestion (Accept/Dismiss) | Officer, Station Officer, Admin |
| `POST` | `/api/v1/inspections/{inspectionId}/checklist/items/{itemId}/evidence` | Attach evidence reference to response | Officer, Station Officer, Admin |
| `POST` | `/api/v1/inspections/{inspectionId}/checklist/complete` | Validate and complete checklist | Officer, Station Officer, Admin |

## 7. Authorization Assumptions

- Inspecting officers authenticated with `ROLE_INSPECTION_OFFICER` are authorized to initialize checklists and record responses for assigned inspections within their tenant.
- Superintending officers (`ROLE_STATION_OFFICER`) and system administrators (`ROLE_ADMIN`) possess supervisory permissions to revise responses and review checklist submissions.
- Strict tenant isolation is preserved on all entities (`tenantId`) and verified via `TenantContext`.
